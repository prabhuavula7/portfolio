## Context

Before operating systems, every application managed its own hardware. Memory allocation, I/O scheduling, process coordination, all of it done by hand, differently, in every program. It worked fine when software was simple. It became a disaster once software grew complex enough that coordinating resources across programs was itself a full-time engineering problem. The OS didn't emerge because someone had a clever idea. It emerged because the alternative was everyone reinventing the same broken wheel, slightly differently, forever.

I keep coming back to this whenever I look at how teams are building agentic systems today. Every team with a production agent is doing the exact same thing: hacking together their own context layer. Prompts that get stuffed until they break, then trimmed until the agent forgets what it was doing. Vector DBs that retrieve chunks that are technically related to the query but practically useless. Session state that resets when it shouldn't and sticks around when it absolutely should not. It's a patchwork of duct tape holding together something that should just be infrastructure.

The patterns are identical across codebases. The bugs, whether the agent forgets what it decided three steps ago or confidently acts on a stale fact from six months ago, all trace back to the same root cause. Context management is unowned infrastructure. Every team is building their own OS from scratch, getting it mostly wrong, and then blaming the model when things fall apart.

What agentic AI actually needs is a ContextOS: a dedicated layer that manages state, memory, and retrieval as first-class system concerns. This is the platform shift that separates agents that work in demos from agents that hold up in production.

## Agents don't fail because of the model

Here's the most common mistake I see in production agent debugging: the team assumes the model is the problem. They run evaluations, try a different model, tweak the system prompt, and wonder why nothing improves. The model was fine the whole time. The context it was working with was a mess.

An agent that forgets what it decided three tool calls ago isn't dumb. It's an agent with broken working memory. An agent that retrieves the wrong context from a vector DB and confidently acts on it isn't hallucinating in the scary AI sense. It's a retrieval failure dressed up as a reasoning failure, which is a much more boring and fixable problem. An agent that starts contradicting itself halfway through a long session isn't losing its mind. It's running out of context window and quietly truncating its own history to fit.

These are all infrastructure failures. The model did exactly what it was supposed to do given the context it received. The context was just wrong.

This distinction matters because it points you at the actual fix. Teams spend months on prompt engineering, model selection, and fine-tuning when the real bottleneck is that nobody has thought carefully about what goes in the context window, when it goes in, how it gets there, and how long it stays. Context is the substrate. Everything else runs on top of it, and you can't fix a leaky foundation by repainting the walls.

## The memory tiers problem

Human cognition has multiple memory systems because they serve different purposes. Working memory holds what you're actively reasoning over right now. Episodic memory stores specific past events. Semantic memory holds general knowledge and facts. Procedural memory encodes learned skills that eventually run on autopilot.

Agent memory systems need the same architecture. Most of them don't have it, and the teams building them often haven't thought about why it matters.

Working memory in an agent is the active context window, what the model can see right now. It's fast, immediately accessible, and extremely limited. Episodic memory is the log of past interactions, decisions, and tool calls, what the agent did in prior sessions with this user or on this task. Semantic memory is the distilled knowledge layer: facts, user preferences, domain knowledge, things that are true independent of any specific session. And then there's long-term procedural memory, which is the most interesting tier: an agent that updates its own system instructions or behavioral defaults based on accumulated experience. Most teams aren't even thinking about this one yet, which is either a missed opportunity or a blessing depending on how your last production incident went.

The failure mode that kills most production agents is conflating all of this. Teams dump everything into the context window until it overflows, or into a single vector DB that treats a user preference from six months ago the same as a document retrieved five seconds ago. Neither approach handles the actual question: which memory tier should own this piece of information, and what are the rules for when it gets promoted, demoted, or expired?

Without a principled answer to that, agents degrade in very predictable ways. They get slower as context grows. They contradict themselves as stale facts survive past their useful life. They lose the thread of long-running tasks because there's no durable episodic layer to fall back on. I hit every one of these failure modes building [Monocular](/projects), an AI-powered project scoping tool. The model was solid. The context management was the actual engineering problem. It always is.

## What the current tool landscape gets right (and misses)

The tool ecosystem has converged around a few serious contenders. They're all doing real work. None of them is what I'm describing when I say ContextOS, and it's worth being specific about the gap.

[Mem0](https://mem0.ai) is the most widely adopted, 48,000+ GitHub stars and a $24M Series A. It's built around a token-efficient memory algorithm using hierarchical extraction and multi-signal retrieval, and it works well for personalization-heavy agents: remember user preferences, surface them at the right moment. The limitation is that Mem0 is fundamentally a memory store. It handles storage and retrieval but doesn't own scope management, handoff protocol, or window budget decisions. It's a very good database that occasionally gets described as an OS.

[Letta](https://letta.ai) (formerly MemGPT, in case you blinked) takes a more interesting architectural bet. Agents actively manage their own memory blocks through tool calls, reading, writing, and searching their own memory archive via explicit function calls. This is closer to what an OS does in spirit. The problem is that it puts the management logic inside the agent rather than in a dedicated layer. That works fine for a single agent. It falls apart in multi-agent systems where context needs to move between agents without each one inventing a handoff protocol that will be confidently wrong in a new and creative way.

[LangMem](https://python.langchain.com/docs/langmem/) is LangChain's entry, an SDK that integrates with LangGraph and supports episodic, semantic, and procedural memory types. Clean integration story if you're already on the LangChain stack. The limitation is baked into what it is: a library, not a service. Memory management is still something your agent code has to explicitly invoke, which means it's still your problem, just with nicer scaffolding around it.

[Zep](https://getzep.com) is the most architecturally interesting of the group. It's built around a temporal knowledge graph called Graphiti that models how facts change over time, not just what's true but what was true when and how it changed. If your agent needs to reason across a fact's history, Zep is the only option that handles it properly. The tradeoff is real complexity and a pretty opinionated data model. Not something you adopt on a Tuesday afternoon when you want a quick win.

Each of these solves a meaningful slice of the problem. None of them is a ContextOS. They're libraries and services that live in userspace. The OS layer is still missing, and the fact that so many smart people are building around this gap rather than at it tells you the right abstraction hasn't clicked yet.

## What ContextOS actually needs to be

The OS analogy is useful because it clarifies scope. An OS isn't a better compiler or a smarter application. It's the layer that sits between the hardware and the programs, managing shared resources so that every program doesn't have to solve that problem from scratch and get it wrong in a unique way.

A ContextOS is the same idea for agents. It's not a model. It's not a retrieval system. It's the layer that sits between your agent runtime and the underlying memory and storage systems, managing context as a shared resource with explicit semantics, lifecycle rules, and access controls.

The core primitives it needs to expose:

- **Memory tier routing**: given a piece of information, the ContextOS decides whether it belongs in working memory, episodic storage, or the semantic layer, and enforces that decision rather than leaving it to every developer to make a different call and get it wrong in a slightly unique way
- **Context window budgeting**: the ContextOS knows the available token budget and makes principled decisions about what to include, prioritizing by recency, relevance, and importance as a combined signal rather than just defaulting to most recent
- **Scope management**: explicit rules for what context a given agent or sub-agent has access to, which prevents context leakage across sessions and context starvation when tasks run long
- **Handoff protocol**: when one agent hands off to another, the ContextOS owns what state transfers, what gets summarized, and what gets discarded, instead of each agent implementing its own version of this and being wrong about it

The companies that build this layer well will have a structural advantage similar to what database vendors had in the 1980s. Every serious application needed persistent state. Every serious application eventually needed a database to manage it properly, because hand-rolling flat file storage at scale is a very fast way to have a very bad time. That wasn't obvious when the flat file approach mostly worked.

We're at that "mostly works" stage right now with context management. Every agent team has their own version of this layer, it's holding together well enough to ship, and nobody is quite ready to admit that what they've built is a database from scratch with worse guarantees. The abstraction moment is coming. The teams building toward it now are going to look very smart in about two years, and everyone else is going to act like it was obvious the whole time.
